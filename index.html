Where does scE2G actually spend its time?

Quantifying the algorithmic complexity of every pipeline step, and the critical path through the Multiome and scATAC DAGs, to direct optimization effort.

Status update · 19 Aug 2026 · measurement in progress

Goal

We want to make scE2G faster. Before optimizing anything, we need to know two things that we currently only guess at: how each step's cost scales with dataset size, and which steps actually determine total wall-clock.

These are different questions. A step can be the slowest single job and still be irrelevant, because it runs in parallel with a longer chain. Conversely a modest step can gate everything downstream. Optimizing the wrong one buys nothing. So the deliverable is a PERT-style job-level graph per modality with the critical path marked, plus a sensitivity analysis: if we speed up rule X, what becomes the new bottleneck?

Scope is the two production models — multiome_powerlaw_v3 and scATAC_powerlaw_v3 — on IGVF10 (6 clusters, realistic sizes, not the largest or smallest we run).

The structural finding that shaped the design

The Multiome/scATAC branch in scE2G is decided per cluster, not per model. The features_required checkpoint reads the cluster's union feature table, and our standard cluster table assigns both models to every cluster — so the Kendall → ATAC-matrix → ARC chain runs once per cluster and is shared by both models, and the scATAC jobs are handed Kendall outputs they don't need. A combined run therefore cannot produce a measured scATAC DAG at all. We split into two runs, one model each, so the scATAC run genuinely resolves to "no Kendall" and we measure its real topology instead of inferring it.

Method

Phase 0 — instrument and measure (running now)

  • A benchmark: directive on every rule across all three nested layers (scE2G → ENCODE_rE2G → ABC) — 46 rules, none of which had one before. Each yields wall time and peak RSS per job.
  • Benchmark paths carry every wildcard, so per-cluster and per-model numbers are never silently averaged together. Verified: 124 jobs, 124 distinct paths, zero collisions.
  • Two full runs on all 6 clusters, one per modality, into separate results dirs. Intermediates and logs are retained for inspection.
  • A toy chr22 run first, as a correctness gate — it reproduces the committed expected outputs exactly. Its timings are deliberately discarded: at a 49 KB fragment file they measure interpreter startup, not algorithm, and would bias every fit.

Phase 1 — characterize each script's complexity

One analyst agent per unique script (deduplicated by script identity — a script shared across modalities or callers has one complexity regardless of who calls it). That reduces 63 script files on disk to 23 script units, plus 3 grouped units for DAG nodes that are pure shell with no script file. Each reads its own source, its rule definition, and its benchmarks across all 6 clusters, then reports complexity derived primarily from reading the code, with the benchmark points used only as a secondary check on the exponent — and flags explicitly wherever the two disagree.

Size variables are chosen per script, not imposed

There is no single "n" for this pipeline. Fragment-processing cost tracks read count; feature-table cost tracks candidate links; some steps scale on a cross term. Phase 0 therefore captures a menu of measured size variables per cluster, and each agent names the one(s) that actually govern its script:

Three functions, not one number

Each script yields t_est(n), t_low(n) and t_high(n) — a calibrated best-guess complexity class plus bounds on the class itself. We deliberately do not collapse these with the textbook PERT formula (O + 4M + P)/6: that assumes point-estimate human uncertainty about a fixed task, whereas our uncertainty is about an exponent. Averaging an O(n) and an O(n²) guess produces a number that is wrong at every scale. Keeping them as functions is what lets us re-evaluate the critical path at different cluster sizes.

Phase 2 — critical path and sensitivity

  • Evaluate each rule's t(n) at each job's actual cluster size, giving a weighted job-level graph per modality.
  • Critical path by summing along cumulative paths — not by picking the slowest single job, since independent branches run concurrently.
  • Recompute at the smallest, median and largest cluster to test whether the critical path is stable or shifts with dataset size.
  • Compute slack for every job; for low-slack rules, ask what becomes the bottleneck if that rule gets substantially faster.

Caveats we're carrying

  • Measurement, not optimization. No rule logic has been changed. The only edits are benchmark: directives and run configuration.
  • Toy-run timings are excluded from all fits — an 85,000× size gap from the real clusters means they measure startup overhead, not scaling.
  • Complexity comes from reading the code first. Six clusters give six points per rule — enough to sanity-check an exponent, not to fit one. Where code and benchmarks disagree, we report the disagreement rather than smoothing it.
  • Shared-filesystem variance is real. Runs are sequential and on non-preemptible partitions so timings aren't contaminated by contention or requeues.
